# DistributionNetworkPlots.jl Architecture

Status: proposed baseline  
Last updated: 2026-09-01

## 1. Purpose

DistributionNetworkPlots.jl is a browser-native explorer for BMOPF distribution-network case files. It provides three coordinated views of the same case:

1. A geospatial view when trustworthy bus coordinates are available.
2. A single-wire electrical diagram.
3. A multi-wire diagram that preserves terminal and conductor detail.

The explorer is delivered as static HTML, JavaScript, CSS, and optional local data files. "Static" means that no application server is required at run time; selection, tooltips, filtering, search, navigation, and drill-down remain interactive in the browser.

The Julia package is the host integration and export API. The browser application owns interaction and rendering.

Implementation sequencing, release gates, and slice-level acceptance criteria are maintained in [ROADMAP.md](ROADMAP.md).

## 2. Goals and non-goals

### 2.1 Goals

- Read BMOPF JSON without sending case data to a server.
- Preserve source records and stable source identities.
- Show consistent asset selection across all three views.
- Make relationships navigable, such as a line to its from/to buses or an IBR to its connection terminals.
- Provide concise tooltips, persistent asset inspection, asset-class summaries, search, and filters.
- Represent terminals, neutrals, grounding, conductor permutations, switches, and multi-winding transformers faithfully.
- Generate a static hosted explorer and portable per-case reports from one frontend implementation.
- Remain useful when a case contains unsupported or newly introduced fields.
- Scale from small teaching cases to realistically sized feeders through progressive rendering and semantic zoom.

### 2.2 Initial non-goals

- Editing and writing BMOPF cases.
- Running power flow or OPF in the browser.
- Displaying time-series animation or solver results.
- Automatically inventing geographic locations for buses without geographic coordinates.
- Guaranteeing a readable full-network multi-wire diagram at every network size.
- Replacing BMOPFTools validation, analysis, or reporting.

These capabilities may be added later without changing the core domain and selection model.

## 3. Architectural principles

### 3.1 One interpretation of the case

Input is interpreted once into a canonical case index. Renderers consume view projections from that index and never parse raw BMOPF records independently.

### 3.2 Preserve source truth

The application retains the original JSON records alongside derived fields. Unknown fields remain visible in the raw-record inspector. Normalisation and layout never mutate the source document.

### 3.3 Devices have ports

The domain model does not assume every asset is a simple graph edge:

- A line or switch normally has two ports.
- A transformer may have two or more winding ports.
- A load, generator, IBR, shunt, capacitor, or source has an attachment port.
- Every port references a bus and an ordered terminal mapping.

Single-wire and multi-wire graphs are projections of this port model.

### 3.4 Selection is renderer-independent

Selection, hover, search, filters, and focus requests live in shared application state. Changing views does not change the selected asset.

### 3.5 Progressive detail

The overview remains legible by collapsing detail. Terminal-level structure is expanded on selection, zoom, or explicit request. Multi-wire focus mode is a first-class view, not merely a temporary implementation shortcut.

### 3.6 Static by default

No runtime backend is required. External network access, including basemap tile access, is optional and disclosed.

There are two supported delivery modes:

- **Explorer:** a static site where a user drops or chooses a local BMOPF JSON file.
- **Report:** a static artifact generated by Julia with a case embedded or colocated.

Both modes use the same core, projections, UI components, and renderers.

## 5. Logical architecture

```text
raw document
    |
    v

    |
    v

    |-- RelationshipIndex
    |-- Diagnostics

shared AppState ------------------+
    |-- selection and hover
    |-- active view
    |-- search and filters

```

### 5.1 Browser core

The browser core is framework-independent TypeScript. It owns:

- Schema-version detection.
- Validation result conversion.
- Stable asset identities.
- Canonical buses, devices, ports, and terminal connections.
- Forward and reverse relationship indexes.
- View projection construction.
- Diagnostics and capability reporting.
- Formatting-safe access to raw records.

The core must not depend on Svelte, the DOM, MapLibre, deck.gl, or SVG.

### 5.2 Application shell

The Svelte application shell owns:

- File selection and drag/drop.
- View switching.
- Shared state and URL/hash synchronisation.
- Asset search, class overview, filters, and legends.
- Tooltip orchestration and persistent inspector panels.
- Loading, empty, partial-support, and error states.
- Responsive and accessible interaction.

### 5.3 Renderers

Renderers receive immutable view projections and shared interaction callbacks. They own visual geometry and camera behaviour, not domain interpretation.

## 6. Canonical domain model

The exact TypeScript types may evolve, but the following concepts and invariants are architectural commitments.

```ts
type AssetKind =
  | "bus"
  | "line"
  | "switch"
  | "transformer"
  | "load"
  | "generator"
  | "ibr"
  | "shunt"
  | "capacitor"
  | "voltage_source"
  | "dc_bus"
  | "dc_branch"
  | "dc_load"
  | "dc_source"
  | "dc_grounding"
  | "other";

type EntityKind =
  | AssetKind
  | "linecode"
  | "line_geometry"
  | "wire_data"
  | "control_profile"
  | "time_series"
  | "terminal_conventions"
  | "other_record";

interface EntityRef<K extends string = EntityKind> {
  kind: K;
  id: string;
  pointer: string; // RFC 6901 JSON Pointer into the source document
}

type AssetRef = EntityRef<AssetKind>;

interface TerminalRef {
  busId: string;
  terminal: string;
}

interface DevicePort {
  id: string;
  role?: string;          // from, to, winding name, connection, etc.
  busId: string;
  terminals: string[];    // ordered source terminal mapping
}

interface CanonicalDevice {
  ref: AssetRef;
  ports: DevicePort[];
  status: "in_service" | "open" | "out_of_service" | "unknown";
  sourceRecord: unknown;
}

interface CanonicalBus {
  ref: AssetRef;
  terminals: string[];
  groundedTerminals: string[];
  coordinates?: Coordinates;
  sourceRecord: unknown;
}
```

### 6.1 Stable identity

`EntityRef.pointer` is the source-of-truth identity. This is important for nested structures such as transformer groups, where a short leaf ID alone may not be globally unique. Rendered network assets use the narrower `AssetRef`; referenced records such as linecodes use the same identity mechanism without pretending to be electrical assets.

Display IDs may be friendlier, but links, selection, caches, tests, and diagnostics use the stable identity.

### 6.2 Relationship indexes

The case index precomputes at least:

- Asset by stable reference.
- Bus by ID.
- Devices incident to each bus.
- Devices incident to each bus terminal.
- Buses referenced by each device.
- Assets grouped by class.
- References to reusable records such as linecodes, control profiles, time series, and wire data.
- Validation and ingestion diagnostics by source pointer.

These indexes make navigation constant-time and keep renderers simple.

### 6.3 Schema versions

The loader reads `meta.$schema` when available and records the detected schema family/version. Version-specific adapters lower supported documents into the canonical model.

Rules:

- Never silently reinterpret an unknown schema version as the latest version.
- Permit partial exploration when safe, accompanied by a visible diagnostic.
- Preserve all unknown fields in `sourceRecord`.
- Keep schema adaptation separate from visual projection.
- Pin fixture expectations to an explicit schema revision.

### 6.4 Derived data and diagnostics

Derived values carry provenance. A coordinate, status, label, voltage level, or phase classification should be distinguishable as:

- Explicitly present in the source.
- Derived without ambiguity.
- Inferred heuristically.
- Unavailable.

Heuristic derivations must produce a diagnostic visible to the user.

## 7. View projections

### 7.1 Geospatial projection

The geospatial projection contains placed buses, device paths or endpoint geometry, feature properties, and coordinate provenance.

Coordinate rules:

- Only coordinates explicitly identified as geographic longitude/latitude are placed directly on a basemap.
- Projected or diagram coordinates are not treated as longitude/latitude.
- A device route is preferred when provided; otherwise a straight segment may join known endpoint coordinates.
- Missing coordinates do not trigger silent synthetic placement on a real map.
- Cases with incomplete coordinates show coverage and omission diagnostics.

MapLibre owns the geographical camera and optional basemap. Native MapLibre GeoJSON layers are sufficient for the initial implementation. A deck.gl overlay may be introduced when scale or richer picking justifies it.

### 7.2 Single-wire projection

The single-wire projection collapses conductor detail while preserving devices and their identity.

Projection rules:

- Buses remain explicit nodes or busbar symbols.
- Lines and switches remain selectable devices.
- Transformers are device nodes or standard symbols with one connection per winding.
- Open and out-of-service assets remain present but are styled distinctly.
- Attachments remain addressable even when drawn as badges or compact symbols.
- Voltage levels, feeder roots, and containment may influence layout without changing topology.

ELK layered layout is the default candidate because it supports explicit ports and orthogonal routing. The prototype now exposes an optional pinned, vendored `elkjs` enhancement from the Single-wire controls; its computed bus positions are calculated in a Web Worker and cached by case identity, direction, and root bus, while deterministic layout remains the offline fallback. Julia-generated reports embed the bundle so the option remains available offline. Production integration still needs production renderer packages and a more formal layout-cache invalidation policy. Layout never mutates the source case.

### 7.3 Multi-wire projection

The multi-wire projection expands ports into terminal-level connections.

Projection rules:

- Conductor pairing follows ordered terminal maps from the source.
- Phase, neutral, and ground are represented distinctly using colour plus labels or line patterns.
- Grounding belongs to bus terminals, not an invented electrical bus.
- Transformer winding ports remain explicit; multi-winding devices are not reduced to arbitrary pairwise branches.
- Unsupported connection semantics produce diagnostics rather than plausible-looking guesses.

The initial renderer supports a selected asset or bus and a configurable one- or two-hop neighbourhood. Full-network overview uses collapsed bundles and semantic zoom; expanded conductors are rendered only where useful.

## 8. Interaction and navigation

### 8.1 Shared state

The minimum shared state is:

```ts
interface AppState {
  activeView: "geo" | "single-wire" | "multi-wire";
  selected: EntityRef | null;
  hovered: AssetRef | null;
  query: string;
  classFilters: Set<AssetKind>;
  focusRequest: FocusRequest | null;
  cameras: Record<string, unknown>;
}
```

Selection is persistent. Hover is ephemeral. A focus request asks the active renderer to frame an asset but does not alter domain data.

### 8.2 Navigation

Related assets in the inspector are interactive references, not plain strings. Examples include:

- Line to from/to buses.
- Bus to incident devices.
- Transformer to all winding buses.
- Asset to linecode or control profile.
- IBR to its connection bus and control record.

Static builds use hash-based URLs so deep links require no server routing. The encoded state includes the active view and stable entity reference. Search/filter state may remain session-local initially.

### 8.3 Tooltip and inspector responsibilities

Tooltips contain only enough information to identify a feature and decide whether to select it. Full properties belong in the persistent inspector.

The inspector is driven by an asset presentation registry that declares:

- Display name and icon.
- Summary fields and units.
- Status formatting.
- Related-object fields.
- Asset-class aggregation fields.
- Optional specialised sections.

Every inspector includes an expandable, safely escaped raw-record view.

### 8.4 Asset-class overview

The overview is derived from the canonical index. Initially it provides:

- Asset counts.
- Visibility/highlight controls.
- Missing-reference and validation counts.
- Basic class-specific aggregates, such as total line length or IBR capacity when safely available.
- A searchable asset list.

Aggregates must state their units, coverage, and exclusions.

## 9. Static packaging and Julia integration

### 9.1 Hosted explorer

The hosted explorer is a normal static build suitable for GitHub Pages or any static host. Local case files are read with browser file APIs and are not uploaded.

### 9.2 Portable report

The Julia API will eventually expose an interface similar to:

```julia
render_case(case, output_path; views=:all, standalone=true, basemap=:none)
```

The exact name is not yet final. Expected behaviour:

- `standalone=true` produces a single portable HTML file when feasible.
- A directory-mode output may use separate hashed assets for better caching and large cases.
- JSON embedding is safe against premature `</script>` termination and HTML injection.
- The package release contains precompiled frontend assets; Julia users do not need Node.js.
- Exporting does not require Julia code to reproduce browser domain logic.

### 9.3 Browser network access

A static artifact can still contact external tile or font services. Supported policies are:

- `basemap=:none`: no external tile dependency; coordinates render on a neutral geographic canvas.
- `basemap=:online`: use a configured map style with attribution and disclose network access.
- Offline tile packaging is deferred until a concrete use case justifies its size and licensing complexity.

### 9.4 Licensing and provenance

- Repository source code is distributed under the BSD 3-Clause License in
  `LICENSE`.
- Original case files authored for this repository are distributed under CC BY
  4.0 in `LICENSE-DATA`.
- Reused cases retain their source initiative's license, attribution, and
  provenance. A fixture directory must carry those notices explicitly; the
  repository code license never relicenses case data.
- Every case should expose its applicable `meta.license`, `meta.attribution`,
  and `meta.source` values when the BMOPF schema permits them.

## 11. Quality attributes

### 11.1 Correctness

- Electrical connectivity takes precedence over visual convenience.
- No renderer may invent a missing terminal mapping.
- Unsupported semantics are visible.
- Every selected visual feature resolves back to a source record.

### 11.2 Performance

- Parsing, projection, and layout are measured separately.
- Expensive parsing or layout runs outside the browser UI thread where possible.
- Layout results are cached by deterministic fingerprints.
- Multi-wire rendering is neighbourhood- and zoom-aware.
- A simple initial renderer is preferred until measured data demonstrates the need for WebGL acceleration.

The browser prototype publishes a conservative initial budget of 500 buses or
5,000 estimated SVG elements. Cases above either threshold keep the indexed
inventory available but switch geospatial and single-wire views to a selected
asset's one-hop context. Final budgets should be recalibrated from measured
micro, small-real, and large fixtures before a production renderer is chosen.

### 11.3 Accessibility

- All essential actions are keyboard accessible.
- Selected SVG assets are focusable and have accessible names.
- Colour is never the only carrier of phase, state, warning, or selection meaning.
- Tooltip content is also available in the persistent inspector.
- Focus remains predictable when switching views or following related-object links.

### 11.4 Security and privacy

- Raw case strings are never inserted as HTML.
- File size, nesting, and element-count limits protect the browser from accidental or hostile inputs.
- External basemap requests are optional and disclosed.
- No telemetry or upload is enabled by default.
- Content Security Policy compatibility is maintained where practical.

### 11.5 Reproducibility

- Schema revision, application version, layout engine version, and case fingerprint are recorded in generated reports.
- Source cases are not mutated by viewing or layout.
- Layout regression tests assert structural invariants; a small number of screenshot tests cover intended visual appearance.

## 12. Testing architecture

### 12.1 Fixture levels

1. **Micro semantic fixture:** hand-authored and permissively licensed; exercises every supported asset and difficult terminal mapping.
2. **Small real fixture:** validates realistic topology and properties.
3. **Large fixture:** exercises performance, density, and progressive rendering.

The micro fixture must include at least:

- Three phases, neutral, and grounding.
- A conductor permutation or missing phase.
- A line and an open switch.
- Two-winding and multi-winding transformer examples.
- A source, load, generator, IBR, shunt, and capacitor.
- An intentionally unsupported or unknown field.
- Coordinates with explicit coordinate-space metadata.

### 12.2 Test layers

- **Core unit tests:** schema dispatch, stable IDs, port construction, reverse indexes, and diagnostics.
- **Projection tests:** topology and terminal-pair invariants for each view.
- **Layout tests:** finite geometry, deterministic ordering where promised, bounds, and port routing.
- **Component tests:** inspector fields, related-object links, filters, and state transitions.
- **End-to-end tests:** load a case, select an asset, navigate to related assets, switch views, and open a generated static report.
- **Visual tests:** a deliberately small set of representative screenshots.
- **Julia tests:** artifact generation, safe JSON embedding, asset inclusion, and public API behaviour.

### 12.3 Cross-view invariants

For every supported selectable asset:

- The same `AssetRef` is used in all views.
- Switching views preserves selection.
- Following an inspector relationship selects the expected target.
- A visual feature links back to exactly one source record.
- Hidden or collapsed detail remains discoverable in the inspector.

## 13. Dependency and reuse policy

- Reuse Tellegen's interaction and visual lessons, and consider shared colour tokens or upstreamable components where boundaries are clean.
- Use Tellegen's browser ingestion as a development oracle or prototype accelerator, not as an unquestioned permanent dependency.
- Prefer BMOPFTools or PowerIO as schema/format authorities instead of creating a competing interpretation.
- Introduce deck.gl only after native MapLibre layers fail an explicit scale or interaction budget.
- Pin layout and schema dependencies for reproducible report generation.
- Record third-party licences and required map attribution in the distributed artifact.

## 14. Architectural decisions

The following decisions are accepted by this baseline unless superseded by an Architecture Decision Record (ADR):

| Decision | Status | Rationale |
|---|---|---|
| Browser-native rendering with a Julia export wrapper | Accepted | Maximises interactivity while retaining Julia ergonomics |
| One canonical port-based model | Accepted | Supports all three views without losing conductor semantics |
| Svelte application shell | Proposed | Matches Tellegen and suits a compact reactive component library |
| SVG electrical diagrams | Accepted for initial releases | Custom symbols, accessibility, inspection, and easy testing |
| ELK/elkjs for diagram layout | Proposed | Supports ports and orthogonal routing |
| MapLibre geospatial camera | Proposed | Open browser mapping stack with local GeoJSON support |
| deck.gl overlay | Deferred until measured | Avoid unnecessary complexity for the first useful slice |
| Hash-based deep links | Accepted | Works on static hosts without route rewrites |
| Multi-wire focus mode first | Accepted | Delivers faithful drill-down before attempting unreadable full expansion |
| No server-side case processing | Accepted | Privacy, portability, and simple deployment |

## 15. Open architectural questions

Resolve these through short spikes or ADRs, not extended design discussion:

1. Should the browser core parse BMOPF directly, wrap a parser-only PowerIO WASM package, or use Tellegen's `ingestDistCase` initially?
2. Which coordinate fields and metadata constitute an authoritative geographic coordinate in each supported schema revision?
3. What is the minimum faithful transformer symbol and port model for every BMOPF transformer form?
4. Should the portable report default to a single HTML file or a directory with cached assets?
5. At what measured case size do SVG and native MapLibre layers require Canvas/WebGL alternatives?
6. Which asset-class aggregates are meaningful and safe across schema versions?
7. Which small real fixture has licensing suitable for redistribution and public previews?
